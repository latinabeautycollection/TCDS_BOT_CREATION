# R1F V2.2 Financial Consumption Hardening

## Purpose

V2.2 converts the V2.1 layer from a mathematically balanced allocation system into a causal, separation-of-duties financial authority.

## Adversarial findings resolved

## Current R1D scraper authority coverage

The financial layer treats the production repository itself as an input authority.

`discover-production-scrapers.ts`:

1. hashes the real production checkout;
2. captures the full 40-character Git commit SHA;
3. reads current certified/effective R1D adapters and their entrypoints;
4. merges approved per-file billing identity overrides;
5. rejects duplicate scraper keys/paths;
6. fails unless the manifest exactly equals that non-empty R1D authority scope.

`register-production-scrapers.ts` refuses registration unless every current adapter has:

- authoritative `retail.retail_platforms.id`;
- Bright Data product type;
- billing authority;
- service type;
- zone for zone-based products, or dataset/collector identifier for cost-breakdown products;
- source SHA-256.

Certification additionally requires every registered current-scope scraper to have execution-receipt coverage **and at least one provider-cost allocation each**. A scraper can therefore be registered but cannot satisfy financial certification until its real execution and billing path have both been exercised.

## Financial authority states

V2.2 intentionally distinguishes:

- `PROVIDER_USAGE_CONFIRMED`
- `PROVIDER_USAGE_ZERO`
- `PROVIDER_PAID_COST_RECONCILED`
- `PROVIDER_ZERO_COST_CONFIRMED`

A zero-dollar Bright Data bucket is legitimate evidence that the provider reported zero billed cost; it is not treated as proof of paid-cost accounting.

## Cost semantics

`provider_billed_cost_usd` is the provider period total.

`allocated_provider_cost_usd` is TCDS's deterministic allocation of that provider total to a job.

The latter is never described as a Bright Data-reported per-job cost unless a future provider endpoint actually supplies job-level cost.

## Bright Data /zone/cost

The collector records the exact provider response and the exclusive `to` boundary. The database derives every `{bw,cost}` bucket from the immutable JSON.

Because the provider sample labels (`back_m*`, `back_d*`) are opaque in the supplied API schema, a bucket cannot become financial authority until a reconciler promotes it to a concrete period with non-empty semantic evidence. That closes the V2.1 double-counting path.

## Web Scraper API / Scraper Studio cost authority

V2.2 includes `collect-brightdata-cost-breakdown.ts`, backed by `POST /costs/export/json`.

Supported dimensions are:

- `web_apis` — keyed by Web Scraper API `dataset_id`;
- `collectors` — keyed by Scraper Studio collector ID;
- `ws_api_snaps` — keyed by Web Scraper API snapshot ID.

The provider response is stored immutably and normalized into one UTC calendar-day authority period per resource. These daily resource costs can bind only to R1D execution receipts carrying the matching dataset, collector, or snapshot identifier.

This means every current R1D scraper can be accounted for according to the Bright Data product it actually uses instead of forcing it into the zone-cost model. Dataset/day allocation is sealed only after complete R1D execution coverage is proven; `ws_api_snaps` is one-to-one direct attribution.


## Security-definer execution model

All V2.2 financial mutation functions explicitly revoke `PUBLIC` execution. `session_user` membership is checked inside `SECURITY DEFINER` functions so the function owner cannot accidentally satisfy the caller authorization gate. Financial table DML remains unavailable to the generic `retail_r1f_worker`; the worker receives only the execution-receipt function required to bind R1D execution facts to an already certified scraper identity.

## Runtime freeze doctrine

This artifact is a hardened **freeze candidate**, not a runtime-certified release. Final Green Tier 1 freeze requires deployment to the target PostgreSQL instance, commit-bound discovery of the current certified/effective R1D scraper scope, complete billing-identity mapping, at least one causal execution receipt and provider-cost allocation for each scraper, live Bright Data provider evidence, adversarial tests, and the normal R1F certification suite.
